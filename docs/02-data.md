# 2. Обрабатываемые данные и формат сообщений

## Допущения для оценки объема

Парк на линии – 1 200 машин в час пик, 900 в среднем; транспорт работает 19 ч в сутки (05:30–00:30). Трекер передает координаты каждые 10 с. В сутки выполняется 950 000 валидаций, 11 % из них приходится на час пик. Размер сообщения – длина компактного JSON примеров из [`examples/`](examples) в UTF-8. Расчет воспроизводится скриптом `python tools/capacity.py`.

## Тип 1. Координаты машины – `vehicle.position`

| Параметр | Значение |
|---|---|
| Название | Отметка местоположения (телеметрия GPS-трекера) |
| Источник | Бортовой GPS-трекер (`trk-NNNNN`), эмулируется Fleet Simulator |
| Основные поля | `message_id`, `type`, `timestamp`, `source_id`, `seq`, `vehicle_id`, `route_id`, `trip_id`, `lat`, `lon`, `speed_kmh`, `heading`, `doors_open` |
| Периодичность | 1 сообщение в 10 с от каждой машины на линии |
| Объем | 1 200 машин / 10 с = 120 сообщ./с в пике × 368 Б ≈ 43,1 КБ/с; 6 156 000 сообщ./сут ≈ 2,1 ГБ/сут |

## Тип 2. Валидация проездного – `ticket.validation`

| Параметр | Значение |
|---|---|
| Название | Проход пассажира через валидатор |
| Источник | Валидатор в салоне (`val-NNNNN-K`, до 4 на машину) |
| Основные поля | `message_id`, `type`, `timestamp`, `source_id`, `seq`, `validator_id`, `vehicle_id`, `route_id`, `trip_id`, `stop_id`, `ticket_type`, `ticket_ref`, `result`, `reject_reason` |
| Периодичность | По событию; 13,9 сообщ./с в среднем, 29 сообщ./с в час пик |
| Объем | 950 000 сообщ./сут × 441 Б ≈ 399,5 МБ/сут; в пике 12,5 КБ/с |

`ticket_ref` – усеченный SHA-256 номера проездного: система считает поток, но не хранит персональные данные.

## Тип 3. Инцидент – `vehicle.incident`

| Параметр | Значение |
|---|---|
| Название | Инцидент с машиной |
| Источник | Водитель (тревожная кнопка), бортовая диагностика; Track Service (`route_deviation`); Schedule Analytics Service (`schedule_deviation`) |
| Основные поля | `message_id`, `type`, `timestamp`, `source_id`, `seq`, `incident_type`, `severity`, `detected_by`, `vehicle_id`, `route_id`, `trip_id`, `lat`, `lon`, `cause_message_id`, `details` |
| Периодичность | Нерегулярно: ~670 в сутки (120 от оборудования, 150 сходов с маршрута, 400 опозданий более 10 мин); до 2 сообщ./с при массовых событиях |
| Объем | 670 × 512 Б ≈ 335 КБ/сут; в пике 1 КБ/с |

## Итог по потоку

| Тип | Размер, Б | Сообщений в сутки | Средняя интенсивность, сообщ./с | Пиковая интенсивность, сообщ./с | Пиковый поток | Объем в сутки |
|---|---|---|---|---|---|---|
| vehicle.position | 368 | 6 156 000 | 90,00 | 120,0 | 43,1 КБ/с | 2,1 ГБ |
| ticket.validation | 441 | 950 000 | 13,89 | 29,0 | 12,5 КБ/с | 399,5 МБ |
| vehicle.incident | 512 | 670 | 0,01 | 2,0 | 1,0 КБ/с | 335,0 КБ |

Пиковая публикация – 151 сообщ./с, доставок потребителям – 271 сообщ./с (координаты копируются в две очереди). В сутки – 7,1 млн сообщений, 2,5 ГБ, за 30 сут – 75 ГБ.

## Формат сообщения

Все сообщения – JSON в общем конверте; тип сообщения совпадает с routing key. Схема – [`schemas/message.schema.json`](schemas/message.schema.json) (JSON Schema 2020-12), примеры – [`examples/`](examples), проверка – `python tools/validate_examples.py`.

```json
{
  "message_id": "3fb6e88d-af4e-5bdc-bf43-8c4dd881ffee",
  "type": "vehicle.position",
  "schema_version": 1,
  "source_id": "trk-10427",
  "seq": 58231,
  "timestamp": "2026-10-12T05:15:30Z",
  "received_at": "2026-10-12T05:15:30.412Z",
  "payload": {
    "vehicle_id": "BUS-10427",
    "route_id": "100",
    "trip_id": "100-A-0815",
    "lat": 53.902284,
    "lon": 27.561831,
    "speed_kmh": 31.5,
    "heading": 74,
    "doors_open": false
  }
}
```

| Поле конверта | Назначение |
|---|---|
| `message_id` | UUID v5 от `source_id:seq` (для событий сервисов – от `cause_message_id:incident_type`). Детерминирован: если устройство повторит отправку после таймаута, шлюз присвоит тот же идентификатор, и потребитель распознает дубликат (ЛР 3) |
| `type` | Тип сообщения и routing key |
| `schema_version` | Версия схемы полезной нагрузки, позволяет менять формат без остановки потребителей |
| `source_id`, `seq` | Источник и монотонный номер события у источника; по `seq` обнаруживаются пропуски |
| `timestamp` | Время события на устройстве (UTC) |
| `received_at` | Время приема шлюзом; разница с `timestamp` – задержка доставки |
| `payload` | Данные, зависящие от типа |

AMQP-свойства сообщения дублируют ключевые поля: `message_id`, `type`, `timestamp`, `content_type=application/json`, `delivery_mode=2` (persistent).

## Хранилище

Схема БД – [`database/init/001_schema.sql`](../database/init/001_schema.sql), проверена на PostgreSQL (`database/tests/smoke_test.sql`).

| Таблица | Владелец (запись) | Содержимое |
|---|---|---|
| `routes`, `stops`, `route_stops`, `route_shapes`, `trips`, `timetable` | Загрузка из ГИС перевозчика | Маршруты, остановки, трассы, рейсы и плановое время прибытия |
| `vehicle_positions` | Track Service | Трек, секционирование по суткам (~6,2 млн строк/сут) |
| `vehicle_state` | Track Service | Последнее положение машины и признак схода с маршрута |
| `stop_arrivals` | Schedule Analytics | Фактическое прибытие на остановку и отклонение от расписания |
| `passenger_flow` | Schedule Analytics | Валидации по маршруту, остановке и 15-минутному интервалу |
| `incidents` | Incident Service | Инциденты, приоритет, статус, связь с повтором |
| `processed_messages` | Все обработчики | Обработанные `message_id` для идемпотентности |
| `rejected_messages` | Все обработчики | Сообщения, не прошедшие проверку, с причиной |
