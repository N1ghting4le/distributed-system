# 6. Анализ архитектуры

## 6.1. Количество компонентов

8 компонентов: Fleet Simulator (источник), Ingest Gateway (Producer), RabbitMQ (брокер), Track Service, Schedule Analytics Service, Incident Service (3 обработчика), PostgreSQL (хранилище), Dispatcher API. Внутри брокера – 1 exchange и 4 очереди. Минимальные требования (1 источник, 1 Producer, 1 брокер, 2 обработчика, 1 хранилище) выполнены.

## 6.2. Основные потоки данных

1. Координаты: трекер → Gateway → RabbitMQ (`vehicle.position`) → Track Service → PostgreSQL (трек, состояние машины).
2. Координаты для аналитики: RabbitMQ (`vehicle.position`, копия) → Schedule Analytics → PostgreSQL (прибытия, опоздания).
3. Валидации: валидатор → Gateway → RabbitMQ (`ticket.validation`) → Schedule Analytics → PostgreSQL (пассажиропоток).
4. Инциденты от оборудования: кнопка/диагностика → Gateway → RabbitMQ (`vehicle.incident`) → Incident Service → PostgreSQL.
5. Производные инциденты: Track Service / Schedule Analytics → RabbitMQ (`vehicle.incident`) → Incident Service → PostgreSQL.
6. Выдача результатов: PostgreSQL → Dispatcher API → диспетчер.

## 6.3. Синхронные и асинхронные взаимодействия

Таблица – в [04-flows.md](04-flows.md#синхронные-и-асинхронные-взаимодействия). Итог: 12 связей, 6 sync (HTTP ×2, SQL ×4), 6 async (AMQP).

## 6.4. Потенциальные узкие места

| Узкое место | Почему |
|---|---|
| Ingest Gateway | Единственная точка приема HTTP; на каждое событие – проверка схемы и ожидание publisher confirm. После восстановления связи сотни машин одновременно отправляют накопленные буферы – кратковременный пик в разы выше 151 сообщ./с |
| PostgreSQL (запись) | ~555 записей/с в час пик (трек, UPSERT состояния, прибытия, пассажиропоток, `processed_messages`), каждая транзакция – fsync журнала; индексы `vehicle_positions` растут на 6,2 млн строк в сутки |
| Schedule Analytics Service | Самая тяжелая обработка (геозоны остановок, сопоставление с расписанием) и состояние в памяти: простое добавление экземпляров нарушит определение прибытий – нужна маршрутизация по `vehicle_id` |
| RabbitMQ (один узел) | Все потоки проходят через один процесс; если обработчики отстают, очереди растут в памяти и на диске, при достижении watermark брокер блокирует публикацию – и Gateway перестает принимать данные |
| Горячая строка `passenger_flow` | В час пик на одной остановке за 15 мин – десятки валидаций, все обновляют одну строку агрегата: блокировки строки |

При росте нагрузки в 10 раз (1 510 сообщ./с, ~5 550 записей/с) первым упрется PostgreSQL: потребуется пакетная запись (COPY / многострочный INSERT раз в 100–500 мс), затем Gateway (несколько реплик за балансировщиком). Track Service масштабируется репликами, Schedule Analytics – шардированием по `vehicle_id`.

## 6.5. Единые точки отказа (SPOF)

- RabbitMQ (один узел) – при отказе между компонентами не передается ничего, Gateway возвращает 503.
- PostgreSQL (один экземпляр) – результаты некуда записать, все обработчики останавливаются, Dispatcher API не отвечает.
- Ingest Gateway (один экземпляр) – устройства не могут передать данные.
- Schedule Analytics (один экземпляр с состоянием) – не SPOF всей системы, но единственная точка для функций «опоздания» и «пассажиропоток».

## 6.6. Последствия отказа отдельных компонентов

| Компонент | Что произойдет | Потеря данных |
|---|---|---|
| Fleet Simulator / устройство | Нет новых событий от машины; по пропуску в `seq` и устареванию `vehicle_state` диспетчер видит потерю связи | Нет (данных не возникает) |
| Ingest Gateway | Устройства получают ошибку соединения и копят события в бортовом буфере | Нет, пока не переполнен буфер устройства; после восстановления – всплеск нагрузки |
| RabbitMQ | Gateway отвечает 503, устройства буферизуют; обработчики переподключаются | Нет для persistent-сообщений в durable-очередях; без publisher confirms – возможна потеря последних сообщений |
| Track Service | Очередь `track.positions` растет (120 сообщ./с ≈ 432 000 за час), карта парка устаревает, сходы с маршрута не выявляются | Нет: сообщения ждут в очереди, неподтвержденные возвращаются в нее |
| Schedule Analytics | Растут `analytics.positions` и `analytics.validations`; опоздания и пассажиропоток считаются с задержкой; трек и инциденты работают | Нет; состояние в памяти восстанавливается по `stop_arrivals` |
| Incident Service | Инциденты ждут в очереди `incidents` – самый критичный по времени отказ (тревожная кнопка) | Нет, но реакция задерживается |
| PostgreSQL | Обработчики не могут зафиксировать транзакцию и не подтверждают сообщения; очереди растут; Dispatcher API недоступен | Нет при ack после COMMIT и Retry (ЛР 3) |
| Dispatcher API | Диспетчер не видит данных; прием и обработка продолжаются | Нет |

## 6.7. Способы повышения отказоустойчивости

| Проблема | Решение | Лабораторная |
|---|---|---|
| SPOF: брокер | Кластер RabbitMQ из 3 узлов с quorum-очередями (репликация по Raft) | ЛР 5–6 |
| SPOF: БД | Потоковая репликация primary/replica и автоматическое переключение (Patroni / CloudNativePG); Dispatcher API читает с реплики | Развитие |
| SPOF: Gateway | Несколько реплик за Kubernetes Service, Gateway без состояния | ЛР 5 |
| Потеря сообщений | Durable exchange и очереди, persistent-сообщения, publisher confirms, ручной ack после COMMIT | ЛР 2 |
| Временные ошибки (БД недоступна) | Retry через exchange `transit.retry` и очереди ожидания `transit.retry.5s/30s/120s` с TTL и dead letter exchange, 3 повтора с растущей задержкой (5, 30, 120 с) | ЛР 3 ✔ |
| «Ядовитые» сообщения | Dead Letter Queue `*.dlq` (exchange `transit.dlx`) после исчерпания попыток или сразу при ошибке структуры, причина в заголовках и `processing_log` | ЛР 3 ✔ |
| Повторная доставка | Детерминированный `message_id` (UUID v5) и таблица `processed_messages` в той же транзакции, что и результат | ЛР 3 ✔ |
| Потеря производного события между COMMIT и publish | При повторной доставке уже обработанного сообщения сервис повторно публикует производные события (их `message_id` детерминирован, Incident Service отбросит дубликат); в перспективе – transactional outbox | ЛР 3 |
| Переполнение брокера при отставании | Лимит длины `analytics.positions` (устаревшие координаты для аналитики не нужны), мониторинг глубины очередей | ЛР 6 |
| Падение экземпляров | Несколько реплик Track Service, liveness/readiness-пробы, автоматический перезапуск Pod | ЛР 4–5 |
| Состояние Schedule Analytics | Consistent hash exchange по `vehicle_id` и восстановление состояния из `stop_arrivals` при запуске | ЛР 5 |
| Нагрузка на запись | Пакетная запись трека, секционирование `vehicle_positions` по суткам | ЛР 6 |

## 6.8. Полный путь данных для сценария `vehicle.position`

Сценарий: трекер BUS-10427 (маршрут 100, рейс 100-A-0815) передает отметку `seq = 58231`; машина в 412 м от трассы (порог – 300 м). Номера шагов соответствуют [диаграмме последовательности](04-flows.md#диаграмма-последовательности).

1. Трекер отправляет `POST /api/v1/events` с `source_id = trk-10427`, `seq = 58231`, координатами и временем события.
2. Gateway проверяет событие по JSON Schema, вычисляет `message_id = 3fb6e88d-…` (UUID v5 от `trk-10427:58231`), добавляет `received_at`, публикует persistent-сообщение в `transit.events` с routing key `vehicle.position`.
3. RabbitMQ записывает сообщение в очереди `track.positions` и `analytics.positions` и возвращает publisher confirm.
4. Gateway отвечает трекеру `202 Accepted` с `message_id`; трекер удаляет событие из буфера.
5. RabbitMQ доставляет сообщение Track Service (оно становится unacked).
6. Track Service проверяет структуру и значения, вычисляет расстояние до трассы (412 м), открывает транзакцию и вставляет `(track-service, message_id)` в `processed_messages` с `ON CONFLICT DO NOTHING`.
7. Вставлена 1 строка – сообщение новое (0 строк означало бы дубликат: транзакция откатывается, сообщение подтверждается без повторной записи).
8. Track Service добавляет строку в `vehicle_positions` и обновляет `vehicle_state` (`off_route = true`) только если отметка новее сохраненной.
9. COMMIT выполнен.
10. Track Service публикует `vehicle.incident` типа `route_deviation` с `message_id = 7c8053a7-…` (UUID v5 от `3fb6e88d-…:route_deviation`) и `cause_message_id`.
11. RabbitMQ подтверждает прием инцидента.
12. Track Service отправляет ack по исходной отметке – сообщение удаляется из `track.positions`.
13. RabbitMQ доставляет инцидент Incident Service из очереди `incidents`.
14. Incident Service назначает приоритет 3 (сход с маршрута), ищет открытый инцидент той же машины за 5 мин и в одной транзакции записывает `incidents` и `processed_messages`.
15. COMMIT выполнен.
16. Incident Service отправляет ack. Dispatcher API при очередном опросе (каждые 5 с) отдает диспетчеру новый инцидент.

Параллельно (шаги не показаны на диаграмме) копию отметки из `analytics.positions` обрабатывает Schedule Analytics: машина не в геозоне остановки, поэтому прибытие не фиксируется.
