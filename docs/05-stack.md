# 5. Технологический стек

| Что выбираем | Выбор | Обоснование |
|---|---|---|
| Язык | Python 3.12: FastAPI + Uvicorn (Gateway, Dispatcher API), aio-pika (AMQP), asyncpg (PostgreSQL), pydantic / jsonschema (проверка сообщений) | Все компоненты – ввод-вывод (HTTP, AMQP, SQL), а не вычисления: асинхронный Python держит сотни сообщений в секунду на экземпляр, требуемый пик – 151 сообщ./с. aio-pika поддерживает publisher confirms и ручной ack, нужные для гарантий доставки. Эмулятор парка и генератор нагрузки (ЛР 2, 6) удобно писать на том же языке. Геометрия (расстояние до трассы, геозоны остановок) – несколько формул в локальной проекции, без тяжелых библиотек |
| Брокер | RabbitMQ 4.1 (management plugin, consistent hash exchange) | Три типа сообщений с разными потребителями – маршрутизация по routing key в topic exchange без кода. Встроенные dead letter exchange, TTL и счетчик `x-death` дают Retry и DLQ (ЛР 3) настройкой очередей. Пик 151 публикаций и 271 доставка в секунду – на два порядка ниже возможностей одного узла. Consistent hash exchange распределяет координаты по `vehicle_id` между экземплярами Schedule Analytics. Management UI показывает глубину очередей – основной индикатор отставания |
| Почему не Kafka | – | Повторное чтение журнала событий полезно для пересчета аналитики, но поток мал для Kafka, а Retry/DLQ и маршрутизацию пришлось бы реализовывать вручную (retry-топики). Kafka станет оправданной при росте до десятков тысяч сообщений в секунду или при необходимости хранить сырые события неделями |
| СУБД | PostgreSQL 17 | Данные структурированы и связаны (рейс – расписание – остановка – прибытие), отчеты – SQL-агрегации. `INSERT … ON CONFLICT` реализует идемпотентность и UPSERT состояния машины, транзакция объединяет запись результата и отметку `processed_messages`. Декларативное секционирование `vehicle_positions` по суткам решает рост трека (2,1 ГБ/сут) удалением старых секций. JSONB хранит трассы маршрутов и отвергнутые сообщения. При росте трека – расширение TimescaleDB без смены СУБД |
| Контейнеризация | Docker, Docker Compose v2 | Семь компонентов с разными зависимостями запускаются одной командой; адреса брокера и БД – через переменные окружения; данные PostgreSQL и RabbitMQ – в томах (ЛР 4) |
| Оркестрация | Kubernetes (Minikube) | Deployment с несколькими репликами Track Service (без состояния) и Gateway, Service для обнаружения брокера и БД по имени, ConfigMap/Secret для параметров, автоматический перезапуск упавших Pod (ЛР 5). StatefulSet для RabbitMQ и PostgreSQL |
| Диаграммы | Mermaid | Диаграммы хранятся в репозитории как текст ([diagrams/](diagrams)), видны в истории изменений и отображаются GitHub прямо в Markdown; PNG для отчета генерируются из тех же исходников |
| Формат данных | JSON + JSON Schema 2020-12 | Человекочитаем при отладке и в журналах, схема проверяется на шлюзе и в сервисах одной и той же библиотекой; объем (до 512 Б на сообщение) не требует двоичных форматов |
