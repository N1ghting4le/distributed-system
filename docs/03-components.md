# 3. Компоненты системы

Сводка: 1 источник данных, 1 Producer, 1 брокер, 3 компонента обработки, 1 хранилище, 1 API – 8 компонентов. Архитектурная диаграмма – [diagrams/architecture.mmd](diagrams/architecture.mmd).

## Fleet Simulator – источник данных

| Параметр | Значение |
|---|---|
| Назначение | Эмулирует бортовое оборудование парка: движение N машин по трассам маршрутов, валидации на остановках, инциденты с заданной вероятностью. Задает интенсивность и объем нагрузки (ЛР 2, 6) |
| Входные данные | Справочники маршрутов и трасс, параметры: число машин, период отправки, интенсивность, доля ошибочных данных |
| Выходные данные | События устройств в JSON: `source_id`, `seq`, `timestamp`, `type`, `payload` |
| Взаимодействие | HTTP POST `/api/v1/events` → Ingest Gateway, синхронно; при ответе 503 или таймауте буферизует событие и повторяет его с тем же `seq` |

## Ingest Gateway – Producer

| Параметр | Значение |
|---|---|
| Назначение | Единая точка приема событий: проверяет структуру по JSON Schema, присваивает `message_id` (UUID v5 от `source_id:seq`) и `received_at`, публикует сообщение в брокер с routing key = `type` |
| Входные данные | HTTP-запрос с одним событием или пакетом до 50 событий |
| Выходные данные | Persistent-сообщение в exchange `transit.events`; ответ 202 Accepted со списком `message_id`, 400 для некорректного события, 503 при недоступности брокера |
| Взаимодействие | HTTP (вход, sync); AMQP 0-9-1 (выход, async) с publisher confirms – 202 отправляется только после подтверждения брокера |

## RabbitMQ – брокер сообщений

| Параметр | Значение |
|---|---|
| Назначение | Принимает, хранит и маршрутизирует сообщения; развязывает Producer и обработчики по времени и по нагрузке |
| Входные данные | Сообщения от Ingest Gateway, Track Service, Schedule Analytics Service |
| Выходные данные | Сообщения в очередях обработчиков |
| Взаимодействие | AMQP 0-9-1, асинхронно. Exchange `transit.events` (topic, durable); очереди (durable, ручное подтверждение): `track.positions` ← `vehicle.position`; `analytics.positions` ← `vehicle.position`; `analytics.validations` ← `ticket.validation`; `incidents` ← `vehicle.incident`. В ЛР 3 добавляются `transit.retry` и `transit.dlx` с очередями `*.retry` и `*.dlq` |

## Track Service – обработчик 1 (валидация и трек)

| Параметр | Значение |
|---|---|
| Назначение | Проверяет координаты (структура, границы города, скорость ≤ 120 км/ч, отметка не из будущего и не старше 10 мин), сохраняет трек и последнее положение машины, определяет сход с трассы маршрута (> 300 м) |
| Входные данные | `vehicle.position` из очереди `track.positions` |
| Выходные данные | Строки `vehicle_positions`, `vehicle_state`, `rejected_messages`; событие `vehicle.incident` (`route_deviation`) |
| Взаимодействие | AMQP consume (async, prefetch 50, ack после фиксации транзакции); SQL к PostgreSQL (sync); AMQP publish инцидента (async с confirm). Без состояния – масштабируется конкурирующими потребителями |

## Schedule Analytics Service – обработчик 2 (расписание и пассажиропоток)

| Параметр | Значение |
|---|---|
| Назначение | По последовательности координат определяет прибытия на остановки (геозона 30 м), сравнивает с расписанием, при опоздании более 10 мин формирует инцидент; агрегирует валидации в пассажиропоток по 15-минутным интервалам |
| Входные данные | `vehicle.position` из `analytics.positions`; `ticket.validation` из `analytics.validations`; справочники `route_stops`, `timetable` (кэшируются при запуске) |
| Выходные данные | Строки `stop_arrivals`, `passenger_flow`; событие `vehicle.incident` (`schedule_deviation`) |
| Взаимодействие | AMQP consume (async); SQL (sync); AMQP publish (async). Хранит состояние машины (предыдущая остановка) в памяти, поэтому несколько экземпляров требуют распределения сообщений по `vehicle_id` (consistent hash exchange) |

## Incident Service – обработчик 3 (инциденты)

| Параметр | Значение |
|---|---|
| Назначение | Регистрирует инциденты, назначает приоритет (1 – тревожная кнопка и ДТП, 2 – поломка и перегрев, 3 – сход с маршрута, 4 – опоздание), связывает повтор того же инцидента той же машины в течение 5 мин с первым |
| Входные данные | `vehicle.incident` из очереди `incidents` |
| Выходные данные | Строки `incidents` |
| Взаимодействие | AMQP consume (async); SQL (sync) |

## PostgreSQL – хранилище

| Параметр | Значение |
|---|---|
| Назначение | Хранит справочники, трек, состояние парка, прибытия, пассажиропоток, инциденты и служебные таблицы идемпотентности |
| Входные данные | INSERT/UPSERT от обработчиков |
| Выходные данные | Результаты SELECT для Dispatcher API и аналитиков |
| Взаимодействие | Протокол PostgreSQL поверх TCP, синхронно |

## Dispatcher API – интерфейс диспетчера

| Параметр | Значение |
|---|---|
| Назначение | Выдает диспетчеру положение парка, отклонения от расписания и открытые инциденты; позволяет принять инцидент в работу |
| Входные данные | HTTP-запросы диспетчера; данные PostgreSQL |
| Выходные данные | JSON: `GET /vehicles`, `GET /routes/{id}/delays`, `GET /incidents?status=new`, `PATCH /incidents/{id}` |
| Взаимодействие | HTTP REST (sync) с клиентом; SQL (sync) с PostgreSQL. В обработке сообщений не участвует |
